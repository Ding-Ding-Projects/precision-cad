# Native update backend foundation

This Qt Core/Network backend is not yet wired into the application shell. It does not establish a complete automatic updater: scheduling, localized user controls, unsaved-work decisions, and installed Squirrel execution evidence remain integration work. No test in this lane launches the host installation's updater or restarts the application.

Production discovery starts from `QCoreApplication::applicationFilePath()`. The executable must reside in `app-<currentVersion>`, below an installation root containing a regular `Update.exe` and `packages/RELEASES`. The manifest must index exactly one matching `PrecisionCAD-<currentVersion>-full.nupkg`, and the installed package must have its declared length and SHA-1. Symbolic links at the named executable, app directory, updater, packages directory, manifest, or package are refused. The current version must come from the running build's provenance. The explicit `setExecutablePathForTesting` seam simulates an executable location, not a production caller-supplied installation root. Standalone development builds report `Unavailable`.

The backend accepts a declared HTTPS metadata feed with no URL credentials. Candidate package and notes URLs must share its scheme, host, and port. The transport deliberately refuses every redirect before requesting its target, including same-origin redirects. It leaves TLS certificate and hostname verification enabled, rejects encoded response bodies, and requires HTTP 200. Feeds must therefore expose their final HTTPS URLs directly. SHA-256 metadata and Squirrel SHA-1 provide package integrity, not publisher authenticity; the feed and updater remain unsigned.

Metadata and RELEASES each have a 1 MiB hard cap. The full package has a 2 GiB ceiling, but its exact RELEASES length becomes the smaller effective download cap. `QNetworkReply` has a 64 KiB read buffer, and response chunks are at most 64 KiB. Content-Length, download-progress totals, incremental byte counts, and the final count are checked. A package is never accumulated into a `QByteArray`. Chunks go directly to `QSaveFile` with direct-write fallback disabled, while incremental SHA-1 and SHA-256 are calculated. A rejected sink, excessive or truncated body, network error, timeout, or cancellation aborts the reply and prevents Ready. The metadata deadline is 30 seconds, and the package deadline is five minutes; these are total deadlines in addition to Qt's transfer timeout.

Before transfer, free space must cover the larger of the configured minimum (64 MiB by default) or twice the declared package length. Production derives its staging root internally as `QStandardPaths::AppLocalDataLocation/updates`; `UpdateConfig` accepts no directory override. A separate `setStagingDirectoryForTesting` seam exists only for isolated fixtures and still passes through every access check. Each candidate gets its own unpredictable UUID directory below that root. The stage contains exactly the validated full package and a canonical single-row RELEASES manifest. The stage is owned by the service and is removed after refusal, cancellation, replacement, or successful child completion. The Windows adapter uses the current process SID, a protected security descriptor, and `CreateDirectoryW` to create each missing directory with exactly two inheritable full-control allow entries: the current user and `SYSTEM`. It then opens the directory using `CreateFileW` with `FILE_FLAG_OPEN_REPARSE_POINT`, reads its actual security descriptor with `GetSecurityInfo`, and checks ownership, DACL protection, principals, inheritance, and access masks. Existing staging roots must already meet that exact private ACL; their owner or DACL is never rewritten. Every existing ancestor down to the current user profile must be canonical, local, non-reparse, owned by the current user, `SYSTEM`, or Administrators, and not writable by another user. Ancestor ownership and write access for `SYSTEM` and Administrators, plus the trusted owner-rights principal, are permitted because same-user processes and administrators are outside this threat model. Root and candidate ownership remain restricted to the current user. UNC paths, paths outside the user profile, junctions, symbolic links, null DACLs, ambiguous ACE forms, and broadly writable parents are refused. Candidate creation and approval verify root and candidate permissions again. Non-Windows hosts refuse this Windows-only backend. These controls protect against other users and unsafe supplied fixture paths, not a process already running as the same user or an administrator.

`requestInstall()` changes Ready to `AwaitingApproval` and emits `restartApprovalRequested(approvalId, version)`. The shell must handle unsaved work and return that exact ID to `approveInstall(approvalId, approved)`. Every request has a fresh opaque ID bound to the candidate generation. Wrong, stale, cancelled, or replayed IDs do nothing. Rejection returns to Ready. Approval re-discovers the installation, re-reads the canonical RELEASES bytes, checks that no extra files or directories appeared, and streams the staged package through both hashes again. Changed bytes or length refuse activation. This closes accidental or pre-approval modification; it does not claim protection from a same-user adversary racing file replacement after validation.

Squirrel.Windows 1.9.1 receives `Update.exe --update=<absolute native directory>` using `QProcess`'s argument vector. A local `file://` URI is not used. The process remains alive after `start()` returns, with asynchronous Started, FailedToStart, and Finished handling. State progresses through `Starting`, `Installing`, and `Installed` only after a normal zero exit code. A nonzero or crashed child reports Error. Standard output and error go to the null device so unbounded logs or installation paths do not accumulate. The backend never invokes a restart command. Installed means that Update.exe reported successful application of the package; the new application has not been launched or verified by this backend.

Keep the service alive until the authorized child finishes. If the service is destroyed first, the child is transferred to application ownership and its unique staging directory is deliberately retained so teardown does not terminate installation or remove the feed beneath it. Closing the entire application can still end an application-owned child; the future shell must prohibit shutdown while installation is active. Retained orphan stages require a later explicitly scoped cleanup; this foundation has no scheduled cleanup worker.

The focused tests cover service validation, exact sizes and hashes, unique staging, same-length digest tampering, post-Ready package and manifest tampering, approval replay across generations, cancellation, and state transitions. A real localhost TLS server checks default certificate rejection, explicit test-CA trust with peer verification retained, a 192 KiB streamed response, oversized headers, chunked overrun, truncated bodies, incorrect declared length, explicit cancellation, deadline expiry, and redirect refusal. Benign child processes check asynchronous start, zero and nonzero exit, failed start, and survival after adapter destruction. Test certificate and key material are generated in a temporary directory and removed after the run, never checked in. These fixtures require Qt Core, Network, Test, and OpenSSL on PATH for temporary certificate generation; the product backend does not invoke OpenSSL.

Build the `precision_update_tests` target and run `ctest --test-dir <build-directory> -R '^precision-update$' --output-on-failure`. The repaired focused suite reports 15 passed, 0 failed, and 0 skipped on Qt 6.8.3 with MSVC 2022. Those results prove backend behavior only. The complete installed update flow still requires an isolated installed Squirrel package, explicit shell approval, real update application, and verification of the restarted version before a complete automatic-updater claim is warranted.

The Windows staging-privacy follow-up rebuilt the test executable and ran the service and ACL subset: 15 passed, 0 failed, and 0 skipped. It verifies real root and candidate owner/DACL descriptors, refusal of a broadly writable existing root without descriptor changes, refusal before creating a child beneath a broadly writable parent, and junction refusal without target mutation. The previously verified TLS and child-process cases were unchanged and were not rerun in this ACL-only follow-up. Service fixtures use isolated temporary directories directly below the user profile; an existing broadly writable AppData or Temp ancestor is an honest unavailable environment, not permission to rewrite its ACL.
