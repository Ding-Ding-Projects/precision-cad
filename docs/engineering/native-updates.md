# Native update client

The native update client is a Qt Core and Network service for the installed unsigned Squirrel.Windows package `PrecisionCAD` version `0.1.0`. It intentionally does not make a standalone development executable look update-capable: an app must have an adjacent `Update.exe` and `RELEASES` file in its owned installation directory before startup or manual checking can run. Other builds report `Unavailable` with that reason.

The service has seven typed states: `Idle`, `Checking`, `Available`, `Downloading`, `Ready`, `Installing`, and `Error`. Startup begins a bounded check once from `Idle`; the UI may also call `checkNow`, `cancel`, and `retry`. A cancelled transfer invalidates its generation and cannot later alter the state. There are no embedded feed credentials and no uncontrolled public "latest" lookup. The configured feed must be HTTPS, have no URL user information, and retain the declared host, scheme, and port across redirects.

Metadata contains the candidate version, release-note URL, full-package URL, and SHA-256. The client refuses a version that is malformed, equal to, or below the running version. It accepts only a same-origin `*-full.nupkg` basename without path separators or traversal. Before package transfer, it fetches the same-origin Squirrel `RELEASES` manifest and requires one valid row for that package. The staged payload must match both metadata SHA-256 and the manifest SHA-1. Staging uses `QSaveFile`, bounded package and metadata sizes, and a free-space check requiring the larger of 64 MiB or twice the package size. Malformed JSON, cross-origin redirects, unsafe paths, missing manifest rows, checksum mismatches, oversized data, and low storage all refuse the candidate.

On a real installed package, the adapter invokes the documented Squirrel executable using `Update.exe --update=<declared HTTPS feed>`. It does not pass arbitrary URLs or user-provided command arguments. Unit tests use a temporary fake process only to prove invocation and refusal boundaries; they do not claim an installed-update proof. Runtime release evidence must still drive the real installer and updater through the documented isolated desktop route.

`requestInstall()` does not invoke `Update.exe`. It moves to `Installing` and emits `restartApprovalRequested`; the app shell must evaluate unsaved work and make an explicit `approveInstall(true)` call. A refusal returns to `Ready`. This service never restarts the application, and therefore cannot discard unsaved CAD work.
